# EchoMind 技术方案 v1.2

## 系统定位

EchoMind（回声）是一个面向中小团队的文档知识库问答系统。核心理念：会议、文档都是"说过的话"，EchoMind 让这些话留下回声——任何时刻提问，都能得到带出处的回答，杜绝大模型幻觉。

## 整体架构

系统采用前后端分离架构。前端使用 React 18 + TypeScript + Tailwind CSS，通过 SSE（Server-Sent Events）接收流式回答。后端使用 Python FastAPI，数据层为 PostgreSQL 16 + pgvector 扩展，缓存层为 Redis 7。

检索链路：文档上传后经解析（支持 PDF、Word、Markdown、TXT、会议转写 JSON 五种格式）、切块（默认 500 字符，相邻块重叠 50 字符）、向量化（bge-small-zh-v1.5，512 维）三步入库。提问时执行混合检索：向量检索（HNSW 索引，余弦距离）与 BM25 关键词检索（jieba 分词）各召回 20 条，RRF 融合后再经 bge-reranker-base 精排出前 5 条送入大模型。

## 关键设计决策

### 为什么选 pgvector 而不是独立向量数据库

中小团队的数据规模（通常百万 chunk 以内）下，pgvector 的 HNSW 索引检索延迟在 10ms 量级，完全够用。同时向量与业务数据（文档、会话）同库，避免了跨库事务一致性问题，运维成本只有一套 PostgreSQL。Milvus、Qdrant 等专用向量库的优势在亿级向量的分布式场景，引入它们对本项目是过度设计。

### 为什么需要混合检索

纯向量检索对语义相近但用词不同的问句表现好（"上线时间"能匹配到"发布日期"），但对专有名词、型号、人名等精确关键词容易漏（问"张伟负责什么"可能检不到含"张伟"的段落，因为向量空间里这不一定最近）。BM25 恰好互补。两路召回用 RRF（Reciprocal Rank Fusion）融合：每个候选的最终得分 = Σ 1/(k + rank_i)，k 取 60。

### 为什么加重排

向量检索是双塔结构，问题和文档分别独立编码，精度有天花板；CrossEncoder 重排把 (问题, 候选段落) 拼在一起送入模型联合打分，能捕捉细粒度相关性，代价是每个候选都要跑一次模型。所以工程上用"粗排召回保效率、精排重打分保精度"的两段式：召回 40 选 20，重排 20 选 5。

## 性能与成本

- Embedding 与重排模型全部本地 CPU 运行，零 API 成本
- 生成使用 DeepSeek API，按 token 计费，单次问答成本约 0.3 分钱
- 热点问题经 Redis 缓存，命中后跳过检索与生成，P95 延迟从 9 秒级降到 50ms 级

## 已知限制与演进方向

当前多轮对话仅携带最近一轮历史，长会话的上下文压缩（滑动窗口 + 摘要）在路线图中。权限体系（空间-角色两层）规划在 V2。评估体系目前以 recall@k 和 MRR 为主，后续引入答案忠实度（faithfulness）的 LLM-as-judge 自动评估。
